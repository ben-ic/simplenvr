# SimpleNVR — Impeccable Design Context

This file captures the design philosophy, visual language, and non-negotiable principles that guide every UI decision in SimpleNVR. It is the single source of truth for design direction. When a proposal conflicts with anything here, the proposal changes — not the document.

Read this file before designing any screen, component, or flow.

---

## Design Context

### Users

**Not** security integrators, IT pros, or datacenter operators. SimpleNVR is for:

- A **a non-technical user** who bought four cameras from Costco to watch the grandkids play in the yard.
- A **dentist** with six cameras across the waiting room and the parking lot.
- A **farm supply store owner** with cameras on the register, the back lot, and the loading dock.
- A **nail salon owner** who checks footage when something seems off, and whose husband set up the cameras.

These users share one thing: **they do not want to think about the technology.** They want something that works out of the box, stays out of the way, and doesn't demand IT knowledge.

**The job to be done:** "Tell me my property is safe, and let me quickly check what happened if something felt off." Every design decision gets filtered through: *what does this user see, feel, and need to do next?*

**Emotional state during use:**
- First launch: nervous, hopeful, a little overwhelmed. Needs reassurance the thing is actually running.
- Daily use: checking in passively. Needs to feel confident at a glance without hunting for information.
- Incident: stressed, focused, time-sensitive. Needs to find a specific moment fast without friction.

### Brand Personality

**Warm, human, grounded.** Not corporate, not enterprise, not cartoonish.

- **Warm** — plain language, encouraging copy, no jargon. "Your cameras are recording" beats "Pipeline active."
- **Human** — speaks like a helpful neighbor, not a product. Owns mistakes in plain words. Never hides behind error codes.
- **Grounded** — confident without being flashy. Quiet competence. The opposite of a demo-driven UI that tries too hard.

**Voice and tone:**
- Speak to a non-technical user, not to a sysadmin. But never be patronizing.
- Short sentences. No exclamation marks. No emojis in product copy.
- When explaining something technical, explain the *outcome*, not the mechanism. ("We're connecting to your camera" — not "Establishing RTSP session.")
- Errors are UX surfaces: what went wrong, in the user's words, and what they can do about it.

### Aesthetic Direction

**Visual tone:** Precision of Linear, warmth of Apple Home's tile paradigm, commercial polish of Stripe's typography. Dark-first. Appliance-like.

**References (what to borrow from each):**
- **Linear / Raycast** — Tight vertical rhythm, high text contrast, disciplined color usage, precise spacing tokens. The "nothing is wasted" feeling.
- **Apple Home / HomeKit** — Tile-based composition, generous padding, large rounded corners, the sense that each element has room to breathe. Built for non-technical users without looking dumbed down.
- **Stripe Dashboard** — Strong typography hierarchy, information-dense-but-calm layouts, the specific quality of looking commercial-grade without being cold.

**Anti-reference:** Never look like a consumer smart-home app. **No** cartoon mascots, **no** pastel spot illustrations, **no** friendly hand-drawn empty states with clouds and stars, **no** gradient backgrounds with soft-clouds-and-dancing-characters. The product is a security tool, not a kids' app.

**Also avoid:** military/tactical surveillance aesthetics (no green-on-black, no radar grids, no mission control). We build for a non-technical user, not SOCOM.

**Theme:** Dark mode is primary. A light mode may come later but every component should be designed dark-first. The existing palette is the foundation:

```
Base background       #0a0a0a    (near-black, not pure black)
Elevated surface 1    #141414    (cards, modals)
Elevated surface 2    #1a1a1a    (toolbars, headers)
Border subtle         #2a2a2a    (dividers inside cards)
Border standard       #333       (card outlines, inputs)
Text primary          #ededed    (main content)
Text secondary        #ddd       (labels, headings)
Text muted            #666       (metadata, timestamps)
Accent — recording    #ef4444    (red — live indicator)
Accent — warning      #fbbf24    (amber — offline, needs-login)
Accent — action       #22c55e    (green — primary buttons, success)
```

**Corner radii:** Generous. 8px for chips/inputs, 10-12px for buttons and small cards, 14-16px for large cards/modals. Apple Home territory, not Windows 95 territory.

**Spacing:** Larger than typical dev-tool density. Cards have 16-24px internal padding. Vertical rhythm is 8/12/16/24/32. No cramming.

**Typography:**
- System font stack (already in place): `-apple-system, BlinkMacSystemFont, "Segoe UI", system-ui, sans-serif`
- Base font size: **15px minimum** (a non-technical user is a real user). Labels and metadata may go to 12-13px but never smaller than 11px.
- Line-height: generous (1.5-1.7 for body text).
- Weight hierarchy: 700 for titles, 600 for labels and buttons, 400 for body. Avoid light weights entirely — they hurt older eyes.

**Motion:** Subtle, purposeful, never decorative. Transitions under 200ms. No parallax, no scroll-hijacking, no bouncy springs. Honor `prefers-reduced-motion` globally (see Accessibility).

### Design Principles

These are the rules every screen must pass. In order of priority:

1. **First principles from the user's perspective.** Every design conversation starts with *"what does the user see, feel, and need to do next?"* — never with *"what's the cleanest implementation?"* If the implementation shows up before the experience is described, stop and start over.

2. **Tell the user what's happening, always.** Never show a blank screen. Never show a spinner without text. Never show an error code without an explanation. "Connecting to your camera..." beats a spinning wheel. "This only happens once on first connect" beats silent waiting.

3. **Zero knobs. Zero jargon.** The user should never see the words "RTSP," "bitrate," "keyframe," "sidecar," "pipeline," or any other implementation detail. If a setting needs to exist, it's in Settings — not in the main flow. If an advanced option exists, it's for Ben the dev, hidden behind an env var, not surfaced to the user.

4. **Teach the product in use, don't precede it.** Onboarding happens on the live dashboard, never in a wizard ahead of it. If the user needs to learn something, they learn it while looking at their own cameras. No screens stand between camera auth and the live view.

5. **Status is communicated by more than color.** Recording, offline, needs-login, warning — every status has a label and/or icon, not just a color. Accessibility is not optional (see below). This is a hard rule.

6. **Defaults that work for a user who dismisses everything.** If the user ignores every prompt, skips every tour, and never opens Settings, the product still works correctly. Onboarding improves the experience but is never required for function. Zero-config is the floor, not the ceiling.

7. **Recover silently. Fail loudly.** Transient hiccups (camera reconnect, ffmpeg restart, network blip) are invisible. The user's mental model is "my NVR just works" — protect it. When something genuinely breaks and requires user action, the message says in plain words what happened and what to do next.

8. **Never patronize. Never punish.** Skip buttons exist on every tour step. Escape hatches exist on every flow. The user is always in control. "Can a non-technical user do this?" is the test for clarity, not permission to be condescending.

### Accessibility (non-negotiable)

These are baseline requirements, not nice-to-haves:

- **Older eyes** — Base font 15px minimum, body line-height 1.5+, AA contrast minimum for all text. 4.5:1 for body, 3:1 for large text and UI components.
- **Reduced motion** — Every animation respects `@media (prefers-reduced-motion: reduce)`. Transitions collapse to instant or to opacity-only crossfades. No parallax, no scroll-linked motion, no auto-play hero videos.
- **Color-blind safe status** — Every status indicator uses an icon, label, shape, or position in addition to color. Recording = red dot **plus** "Recording N cameras" text. Offline = amber **plus** "offline" label **plus** a dimmed state. A deuteranope must be able to use the app without ambiguity.
- **Keyboard navigation** — Full keyboard operability. Every interactive element has a visible focus ring (not the browser default — a designed one, 2px solid green accent with 2px offset). Tab order follows visual order. Escape closes modals. Enter confirms primary actions. Common flows (camera setup, browse footage) have keyboard shortcuts.

### Layout Archetypes

Existing and sanctioned:

- **Split view** — HistoryPanel (left, resizable) + main stage (right). Used on Home. The left panel is where "what happened" lives; the right is where "what's happening" lives.
- **Tile grid** — 1-4 cameras → 2 columns, 5+ → 3 columns. Generous 8-12px gutters. Tile corners: 8px.
- **Modal over dimmed backdrop** — For Settings and per-item edits. Backdrop `rgba(0,0,0,0.65)`. Modal: 14px corners, 24px internal padding.
- **Inline prompts on tiles** — For camera naming and similar lightweight interactions. Gradient fade from transparent to `rgba(0,0,0,0.95)` at the bottom of the tile, 28px top padding to preserve the feed visibility.

### Forbidden patterns

- Wizards between camera auth and live view. Dashboard-first, always.
- "Drag and drop to continue" as a gate. Drag-and-drop may exist as an optional affordance but never as the required path.
- Cartoon empty states with clouds, characters, or hand-drawn props. Empty states are a single line of text and a subtle illustration made from existing UI elements (dotted outlines, placeholder tiles).
- Auto-playing audio. Ever. Live video tiles start muted.
- Modal dialogs for recoverable errors. If something can be retried, show a banner, not a modal.
- Names of competing NVR products anywhere in code, commits, copy, or UI.

## Check before shipping a design

Run through these questions. If any answer is "no" or "unclear," the design isn't ready.

1. Can a non-technical user do this without asking someone?
2. Does the first screen the user sees tell them what's happening?
3. Is every status communicated by more than color?
4. Does the skip/escape path exist and work?
5. Does the design respect reduced motion?
6. Is the base font size 15px or larger?
7. Are error messages written in the user's words, with a clear next step?
8. Does the user see their own cameras (or a path to them) within 3 interactions of launch?
9. Does anything in the design require the user to know what "RTSP," "codec," or "bitrate" means?
10. Would this feel at home next to Linear, Apple Home, and Stripe — or does it feel like a consumer gadget app?
